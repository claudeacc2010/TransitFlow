/# TransitFlow — доработка деталей (v2)

Документ описывает доработки «настоящей логистики» поверх Этапов 0–2.
Приоритеты выставлены с учётом дедлайна **12 июня 09:00** и того, что Этап 3
(демо, видео, презентация) ещё впереди.

Легенда приоритетов:

- **P0** — делаем обязательно, дёшево и сильно цепляет жюри;
- **P1** — делаем, если P0 закрыт и осталось время;
- **P2** — только витринно (отображение без логики) или режем.

---

## 1. Характеристики груза в заявке — P0

**Что.** Заявка — не просто «груз 22 т», а полноценная спецификация.

**Модель** (`backend/app/models.py`, `CargoRequest` — новые колонки):

| Поле | Тип | Пример |
|---|---|---|
| `volume_m3` | Numeric(10,2), nullable | 36.0 |
| `adr_class` | String(8), nullable | `"3"` (null = не опасный) |
| `temp_mode` | String(32), nullable | `"+2..+6"` (null = обычный) |
| `ready_at` | DateTime(tz) | 12 июня 18:00 |
| `urgency` | Enum: `normal` / `urgent` | `urgent` |

`cargo_type` расширить: `container, bulk, liquid, general` → добавить
`food` (продукты), `grain` (зерно), `oil_products` (нефтепродукты),
`construction` (стройматериалы), `chemicals` (химикаты).

> ⚠️ Postgres-enum'ы мигрировать больно. На хакатоне честный путь:
> `drop_all/create_all` + перезапуск `seed.py` (сид дополнить новыми полями).
> Это же закроет баг с «Лаура Бекова» в сиде.

**API.** Расширить Pydantic-схемы создания/чтения заявки (`schemas.py`,
`serializers.py`, `routers/requests.py`). Валидация: `adr_class` only ∈
{1..9}, `weight_t > 0`.

**UI.** Форма создания заявки у shipper — новые поля (селекты + чекбокс ADR
+ температура). Карточка заявки — бейджи: `ADR 3`, `❄ +2..+6`, `Срочно`.

**Оценка:** ~1.5–2 ч вместе с сидом.

## 2. Цены и маркетплейс «как Яндекс Такси» — P0

**Что.** Отправитель ставит цену за перевозку; перевозчик видит доску
заказов с ценами и сам выбирает. Система подсказывает рекомендованную цену
от точки А до Б с учётом условий.

**Модель.**
- `CargoRequest`: + `price_offer` (Numeric(12,2), тг) — цена отправителя;
  + `distance_km` (Numeric(8,1)) — берётся из справочника маршрутов (см. §4).
- Новый справочник тарифов не нужен — рекомендация считается формулой.

**Рекомендованная цена** (`backend/app/pricing.py`, чистая функция):

```
base = BASE_RATE_TENGE_PER_KM_T * distance_km * weight_t
коэффициенты: ADR ×1.3, температурный режим ×1.2, urgent ×1.15,
              liquid/oil ×1.1
recommended = base * Π(коэффициентов)
```

`BASE_RATE_TENGE_PER_KM_T` — константа в конфиге (например, 25 тг/км·т).
Эндпоинт `POST /api/requests/recommend-price` — принимает черновик заявки,
возвращает `{recommended, rate_per_km, factors: [...]}`. Показывать
разложение по факторам — это и есть «вау» для жюри.

**Средняя рыночная цена.** `GET /api/analytics/market-rate` — среднее
`price_offer / distance_km` по закрытым заявкам (тг/км). Показывать на доске
заказов и в дашборде аналитика.

**UI.**
- Shipper: при создании заявки после выбора маршрута и параметров — блок
  «Рекомендованная цена: 412 000 тг (19,6 тг/км·т)» + поле своей цены.
  Если своя цена ниже рекомендованной на >20% — мягкое предупреждение
  «перевозчики могут не взять».
- Carrier: доска открытых заявок = карточки с ценой, **тг/км**, маршрутом,
  бейджами груза; сортировка по цене/тг/км. Кнопка «Взять заказ» — это уже
  существующий `accept`, менять механику не надо.

**Оценка:** ~2–2.5 ч. Самая «продуктовая» фича — делает из CRUD маркетплейс.

## 3. Реальные статусы перевозки — P0

**Что.** Жизненный цикл груза вместо «создано/принято».

**Модель.** Не ломать `RequestStatus` (на нём держится маркетплейс), а
добавить **транспортный статус на Assignment**:

```python
class ShipmentStatus(str, enum.Enum):
    confirmed        = "confirmed"         # подтверждено перевозчиком
    awaiting_loading = "awaiting_loading"  # ожидает погрузки
    in_transit       = "in_transit"        # в пути
    at_checkpoint    = "at_checkpoint"     # на пункте пропуска
    at_port          = "at_port"           # в порту
    delivered        = "delivered"         # доставлено
```

`Assignment`: + `shipment_status` + `status_updated_at`. Маппинг общей
картины: `open` = «ищется перевозчик», дальше — по shipment_status.

**API.** `PATCH /api/assignments/{id}/status` — только carrier-владелец,
только переход «вперёд» по цепочке (валидировать порядок). При `delivered`
проставлять `RequestStatus.done`. Каждый переход попадает в ленту событий
(routers/events уже читает таймстампы — добавить источник).

**UI.** У shipper в карточке заявки — горизонтальный степпер
(Создана → Ищется перевозчик → Подтверждено → Погрузка → В пути →
Пункт пропуска → Порт → Доставлено). У carrier — кнопка «Следующий статус».

**Оценка:** ~1.5 ч. Степпер визуально очень выгоден на демо.

## 4. Настоящие маршруты с рекомендацией — P1

**Что.** Не «Актау → Бейнеу», а маршрут с промежуточными узлами, и система
рекомендует вариант с учётом загруженности.

**Модель.** Новая таблица `Route`:

| Поле | Тип |
|---|---|
| `origin`, `destination` | String |
| `waypoints` | JSON — список `{name, checkpoint_id?}` |
| `distance_km` | Numeric |
| `base_hours` | Numeric |

Сид: 2–3 пары с альтернативами, например
`Актау → Бейнеу` напрямую (520 км) и через `Жетыбай` (590 км);
`Актау → граница Туркменистана` через порт и через автопереход.

**Рекомендация.** `GET /api/routes/recommend?origin=&destination=`:

```
score = base_hours + Σ est_wait_hours(checkpoint) по waypoints с checkpoint_id
```

`est_wait_hours` — из §5. Ответ: оба маршрута + `recommended: true` у
лучшего + причина («дольше на 70 км, но экономия 7 ч в очереди»).

**UI.** При создании заявки shipper выбирает направление → видит сравнение
двух карточек маршрутов (км / часы / ожидание) с пометкой «Рекомендуем».
Выбранный маршрут даёт `distance_km` для цены (§2) — поэтому §4 лучше
делать сразу после §2, либо на первый шаг захардкодить расстояния в
справочнике направлений без таблицы.

**Оценка:** ~2 ч. Если время жмёт — таблицу не делать, справочник маршрутов
держать в Python-словаре (для демо неотличимо, Postgres-требование кейса
покрыто остальными данными).

## 5. Реалистичные очереди — P0

**Что.** «Пропускная способность 250 машин/сутки, ожидают 310 → ожидание ~8 ч».

**Данные уже есть:** `Checkpoint.capacity_per_hour`, брони (`Booking`) со
статусами `booked/arrived/passed`.

**API.** Расширить ответ `routers/checkpoints.py`:

```
waiting_now     = COUNT(bookings: status in (booked, arrived), сегодня)
capacity_day    = capacity_per_hour * 24
est_wait_hours  = max(0, (waiting_now - capacity_per_hour) / capacity_per_hour)
```

(формулу можно упростить до `waiting_now / capacity_per_hour` — главное,
чтобы цифры на демо выглядели правдоподобно; подкрутить сид, чтобы в порту
Актау была очередь, а на альтернативном узле — нет: это питает рекомендацию §4).

**UI.** На карте дашборда в попапе узла и в кабинете carrier:
«Ожидают: 310 · Пропускная способность: 250/сутки · **Ожидание ≈ 8 ч**».
Цвет маркера по уровню загрузки (уже есть load — переиспользовать).

**Оценка:** ~1 ч. Это центральная боль кейса — обязательно.

## 6. Документы и совместимость грузов — P0 (витринно)

**Что.** Системе не нужен документооборот — достаточно подсказывать.

**Реализация — чистые функции без БД** (`backend/app/cargo_rules.py`):

```python
def required_docs(req) -> list[str]:
    docs = ["CMR", "Накладная"]
    if req.adr_class:        docs.append(f"ADR (класс {req.adr_class})")
    if req.cargo_type == food:  docs.append("Ветеринарный/санитарный сертификат")
    if req.cargo_type == grain: docs.append("Фитосанитарный сертификат")
    return docs

INCOMPATIBLE = {food: {chemicals, oil_products}, ...}  # симметрично
```

**UI.** В карточке заявки блок «Потребуются документы: CMR + ADR (класс 3)»
и бейдж «⚠ Нельзя совмещать с: продукты питания» на карточке у перевозчика.

**Оценка:** ~40 мин. Минимум кода, максимум «они понимают логистику».

## 7. Аналитика для акимата — P1

**Что.** Превратить графики в инструмент управления регионом. База уже есть
(overview/timeseries/breakdown) — добавить три блока:

1. **Структура грузопотока** — донат по `cargo_type` в % («нефтепродукты —
   35%»). Скорее всего breakdown уже близок — довести до процентов.
2. **Узкие места** — топ-3 чекпойнта по `est_wait_hours` из §5
   («Порт Актау — 8 ч, Бейнеу — 3 ч»).
3. **Пик нагрузки по дням недели** — агрегат `TrafficHistory` по dow
   («понедельник и четверг — пик»). Гистограмма из 7 столбцов.

AI-сводку (§Gemini) дополнить этими данными в промпт — она сама начнёт
писать «рекомендуем увеличить смены в порту по понедельникам».

**Оценка:** ~1.5 ч.

## Порядок внедрения (с оглядкой на дедлайн)

| Шаг | Что | Время | Приоритет |
|---|---|---|---|
| 1 | §1 Поля груза + пересоздание БД + сид | 2 ч | P0 |
| 2 | §5 Очереди (ожидание на узлах) | 1 ч | P0 |
| 3 | §2 Цены + доска заказов carrier | 2.5 ч | P0 |
| 4 | §3 Статусы + степпер | 1.5 ч | P0 |
| 5 | §6 Документы/совместимость | 0.5 ч | P0 |
| 6 | §4 Маршруты с рекомендацией | 2 ч | P1 |
| 7 | §7 Аналитика акимата | 1.5 ч | P1 |

Итого P0 ≈ 7.5 ч, P0+P1 ≈ 11 ч. **Этап 3 (демо, видео, презентация,
письмо к 08:00) требует ещё 3–4 ч — его резать нельзя.** Если времени
впритык: §4 делаем на Python-словаре маршрутов, §7 урезаем до пункта 2
(узкие места — он питается из §5 бесплатно).

Технические заметки:
- Все enum-изменения — через пересоздание БД + сид (Alembic на хакатоне — трата времени).
- После каждого шага — дополнить smoke-скрипт и прогнать на живой БД.
- Бэкенд на Windows перезапускать руками (без `--reload`).
